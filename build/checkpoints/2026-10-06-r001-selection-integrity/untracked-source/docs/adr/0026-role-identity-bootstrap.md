# Fixed service-identity bootstrap

R0.04's real CLI inventory reports all eight canonical service accounts missing. The existing Ops owner gains `RoleIdentityBootstrap.run`: `toy bootstrap identities --plan --request-id <UUID> --json` prepares the fixed operation; applying it requires `--expected-snapshot <SHA256>` and an already-root caller. The CLI never invokes sudo, an administrator dialog, arbitrary shell text or a caller-selected executable/path/UID. This is the initial builder bootstrap, not a model-visible maintenance operation.

The protected implementation accepts the canonical request over a private pipe. It reads the local Directory Service UID/GID inventory and checks the fixed root's parents. Candidate IDs are vacancies observed in the local service-ID range 300–499, never assigned identity evidence. A changed snapshot, occupied role name, existing Toy root, unsafe parent, malformed query or exhausted pool refuses before mutation. Existing accounts, groups, sudo policy, profiles, Chrome, gateway and old core are untouched.

The only write scope is eight new dedicated service groups/accounts and the declared new Toy root/control/state/run/private-home directories. Each account gets its own generated Directory Service ID, primary group, hidden/non-login shell and explicit disabled authentication through `pwpolicy`; no password is generated or put in argv. The root implementation never starts a service or changes an existing record. Account creation and directory ownership require independent readback. A failure after effects returns partial/unknown and stops; it does not delete or adopt a partial account on retry. This first bootstrap version requires a completely absent target, so existing or partial installations remain a typed conflict for the maintenance owner.

The root records the nonsecret bootstrap report under its newly protected control directory. This is prerequisite evidence, not the complete installed-services manifest. Reports structurally keep `identityGateVerified`, `maintenanceIdentityVerified` and `servicesActivated` false. The independent maintenance/recovery identity, immutable control/runtime installation, complete role/socket/credential manifest and actual-UID denial matrix remain required before live use. No R0.04 AT is passed by a plan or non-root refusal.

The source/type/CLI preparation gate uses real read-only planning plus refusals for non-root apply, invalid/missing snapshot, caller UID/path overrides and test-environment selection. Root account changes remain unexecuted in this managed session, whose filesystem does not allow installation outside the workspace. No bypass through another surface is permitted. The bootstrap is implemented inside the existing protected control area with TypeScript and standard macOS tools; no new module, dependency, IPC service or Swift artifact is added.

Primary command evidence is Apple's [Directory Service account example](https://developer.apple.com/library/archive/documentation/Porting/Conceptual/PortingUnix/additionalfeatures/additionalfeatures.html) and [UID/GID allocation example](https://developer.apple.com/library/archive/documentation/OpenSource/Conceptual/ShellScripting/StartingPoints/StartingPoints.html), checked 2026-10-06 against installed `/usr/share/man/man1/dscl.1` and `/usr/share/man/man8/pwpolicy.8`. The installed manual documents `-disableuser`. These establish command shape, not runtime success on this Mac; actual root/bootstrap and denial evidence remains pending.
