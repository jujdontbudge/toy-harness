# Protected SIWC credential owner

R0.01 requires an independently acquired Toy grant, stable host/registration identity and exact save/readback. The authorization coordinator's credential-owner seam was unbound. The existing protected Secrets area owns its implementation; agent packages and the CLI cannot import it. The authorization coordinator moves into that same protected host so OAuth credentials are collected there; Hermes no longer exports it.

`SiwcGrantOwner` implements the canonical `SiwcCredentialOwner` interface. It stores one versioned vault item containing host UUID, selected registration, pending issued client ID and complete grant. `load`, `retainClientId`, `save` and `read` preserve the selected identity and refuse a registration change. Each authorization coordinator owns its own owner instance. Load captures its predecessor; retain and save condition writes on that captured digest rather than adopting a concurrent writer's newer grant. Initial host creation and all changes compare the previous content digest before writing; conflicts refuse the attempt. The complete item changes atomically and is independently read back. Read never creates an item. Authorization alone cannot set zero-credit eligibility.

The only persistence seam is the external OS Keychain. The native adapter uses the standard-library Python ctypes bridge to the installed macOS Security/CoreFoundation frameworks, with the narrow generic-password SecItem APIs. A fixed Keychain service/account stores the opaque canonical JSON bytes; the generic attribute holds their SHA256 digest for conditional update. No delete operation, file fallback, token argument, shell, interactive password automation or model-visible secret operation exists. The helper accepts bytes through its private stdin pipe and returns bytes only to its protected parent. It checks the actual `_toy_control` UID before any Keychain call. Importing source launches nothing.

The public vault schema and secret-bearing transient types live only in contracts and generate TypeScript/Python forms. The helper treats stored bytes as opaque; the TypeScript owner validates canonical contents. `createSiwcAuthorization` assembles a new protected owner and native store for one coordinator. Its private launcher configuration requires the selected Python executable plus interpreter/helper digests from the approved Ops runtime manifest; both digests are checked before every spawn. There is no tooling-interpreter default or environment-selected executable. Configuring these fields alone is not admission or a runtime attestation. The installed SDK headers are the bounded local API evidence for the implementation. Swift generation/compilation remains deferred to R3.

Source/type/lint verification can proceed in this checkout. Live Keychain behavior, actual protected parent/child identity and permissions, admitted CLI auth subprocess fixtures, fresh restart/refresh, broker binding and account-specific zero-credit readback remain required. This source preparation does not establish any whole R0.01 or R0.03 acceptance verdict and does not install or mutate an existing profile, credential, service or account. The default native adapter must be hosted by the protected control process after its identity and child-admission predicates pass. Human consent waits for that concrete secure host; the prepared authorization coordinator remains unlaunched.
