# Bootstrap attempt ownership and recovery

Status: bounded implementation contract, not executable admission or acceptance. The current private journal and read-only resource measurement are implemented under ADRs 0014–0015. Runtime ownership, sole-lease enforcement, signing, descendant recovery and cleanup remain unavailable. The measured headroom deficit independently blocks execution.

## One owner

The public interface remains `OpsTestStack.up/down`. Ops owns the entire attempt behind that interface: normalized intent, durable generation, resource measurement, sole-lease reservation, staging, signing, native execution, evidence projection and reconciliation. The CLI supplies no path, executable, argv, UID, resource proof, expected result or lease capability. The owner uses generated Contracts types before any new transport or journal representation is implemented.

One foreground Ops attempt process runs under the ephemeral caller-domain launchd job selected in ADR 0010. It uses the pinned, digest-bound Node runtime with `--jitless` and the compiled Ops implementation. It is outside the target sandbox and may launch only the immutable registered native closure. Its label, input/output locations and minimal environment derive from the allocated stack and generation. Neither a caller-supplied label nor a production/system-domain job is accepted. The domain, exact owner incarnation, code closure and job registration must be independently read back before native work. No permanent gateway, service account or production datastore is added by this bootstrap owner.

Launchd provides external process lifetime and restart behavior; it does not supply the attempt deadline. The installed manual states that `TimeOut` is unimplemented, while `ExitTimeOut` only bounds TERM-to-KILL escalation after a stop request. `KeepAlive` restart conditions and throttling therefore cannot be treated as deadline enforcement. `AbandonProcessGroup` stays false, but process-group cleanup is supplementary evidence: a surviving or escaped descendant leaves cleanup incomplete. These API observations are not a measured job or recovery result.

The foreground owner enforces one real deadline beginning before staging/signing and covering every helper, read, acknowledgment and cleanup reserve. Native signature/hash calls run in the separately supervised native process rather than blocking that owner's event loop. OS subprocesses use asynchronous bounded collection, fixed arguments and minimal environment. A stopped native process cannot prevent the external owner from reaching its deadline. Cancellation, pressure loss or expiry fences effects first, then reconciles owned resources. Killing a PID without checking its recorded incarnation is forbidden.

## Durable fencing and the sole lease

The journal binds request, operation, stack, generation, boot session, owner incarnation, closure digest, real expiry and every resource/process incarnation. A reservation never grants a runtime permit by itself. Only fresh host measurements, an exclusive current lease, independently admitted aggregate enforcement, actual required identity/authorization and verified artifact closure can grant one. Doctor remains read-only and reports the measured owner/enforcement availability; it never returns a capability.

The lease has one singleton active slot enforced by a database constraint and transactional compare-and-swap against the current generation. A private caller-owned bootstrap slot proves only serialization of its admitted bootstrap participants. It cannot certify the protected production global lease, legacy work, actual service identities or an unimplemented participant. Those distinctions remain in readiness and evidence. All admitted bootstrap heavy work must use this one owner; no controller-local fallback or second lease store is permitted.

Lease expiry, owner death, reboot or missing IPC changes the attempt to reconciliation-required. None automatically frees the slot. A replacement owner fences the old generation and verifies journal integrity, exact immutable closure, boot/session and kernel process incarnations before doing anything. It may signal only recorded resources still demonstrably owned by that generation. PID reuse, unknown ownership, mismatched files, an unverified container or an unknown descendant preserves the lease and unresolved references. The next admission must reconcile a prior slot before reserving a new one; it cannot overwrite uncertainty. Unexpected-exit launchd recovery must use the same generation and recovery path, with bounded backoff and no automatic replay of effects.

Every native child must be independently identified and durably recorded before an acknowledgment allows its next effect phase. The present final entry receipt arrives too late to be the complete recovery ledger. The native protocol must therefore add closed ownership events and acknowledgments before it is used for executable admission. The outside owner samples live PID/PPID/UID/GID/birth and code identity, persists that binding, then acknowledges. A dropped pipe or owner death leaves the child in a bounded waiting/exit path. Future PostgreSQL forks/session changes need their own complete tree accounting; the one-shot parent/child prototype proves none of that behavior.

Release requires fenced work, independently observed terminal native processes, accounted-for files/container metadata/job registration and an archived safe terminal result. An exit code or a parent-reaped flag is insufficient. A lease remains held while any required cell is unresolved. Terminal blocked V1 requests retain their identities and cannot be retried into executable work under the same request key.

## Backup before journal migration

The existing version-1 store is not replaced or modified silently. Before adding lease, transition or process-ledger tables, the same journal owner creates a SQLite online backup through the pinned Node API into an exclusively allocated, owner-only fixed backup area. The source remains validated against its complete V1 schema and owner binding. A separate read-only connection checks the backup's integrity, expected schema and owner/store identity; its exact byte digest and permitted record counts are durably recorded before migration begins. The backup is retained. A raw copy of a live WAL database is not a backup.

The new storage inventory, migration manifest and receipt schemas must be generated first. Migration then uses an explicit version transition with transactional schema replacement, exact post-migration closure readback and preservation of all existing request/operation/event identities. Existing blocked terminal rows remain immutable. Unknown versions, source drift, failed backup verification, incomplete migration or ownership mismatch fail closed. Recovery never deletes a store, overwrites its backup or attempts an automatic downgrade. The public CLI must exercise the migration by reaching the real owner; no private-function or direct-SQL behavioral test substitutes.

The bounded V1-to-V2 transition keeps all V1 tables/triggers unchanged and adds an immutable migration ledger plus empty owner and work-lease tables. A partial unique index allows only one held/reconciliation-required lease slot. This is storage preparation; no owner/lease row or runtime permit is created. The lease/owner schemas bind boot session and full process incarnation; admitting those records requires the later external owner implementation.

Backup files stay in the existing private control root, under owner-derived `backup.<UUID>` names. A fsynced generated intent reserves each name before its exclusively created empty database file is passed to SQLite. A completed, independently checked snapshot receives a separate fsynced generated receipt. No verified or failed snapshot is overwritten or removed; failed attempts retain their files, and a bounded later attempt uses a new UUID. Inventory checks recognize only fixed intent/database/receipt/SQLite-sidecar members whose intent belongs to this store. Unrecognized files fail closed. This avoids another directory/ownership root and an unjournalled directory-adoption path.

The same write reservation excludes concurrent journal writers while a separate read connection supplies SQLite's online backup. V2 is committed only after source/backup integrity, exact V1 schema, complete logical rows and owner/generation/count bindings agree. Deep doctor adds the registered `bootstrap.journal` inspection, which opens an existing store read-only and never initializes or migrates it. Its PASS means only the retained backup and private V2 storage verified; all 25 unavailable owner probes, incomplete overall verdict, absent runtime ownership and protected global lease remain explicit.

## Bounded implementation and proof

First implement the generated migration/backup/state interface and the existing journal owner's online-backup/version transition. Verify existing blocked requests through separate packed CLI retries before and after that transition, with an external OS/storage fault fixture for interrupted paths. No native effect is authorized by this work.

Then implement the single external attempt process and generated ownership-event protocol. Verify through registered `toy` cases: competing requests, repeated identity, stop/continue, dropped or trailing frames, expiry, owner death, stale generation, PID reuse, swapped artifacts, pressure loss, failed suspension, unknown/escaped descendants and retained unresolved cleanup. Fakes belong only to the external OS/provider seams; protected expectations stay outside the target. Resource/identity/artifact readiness must fail closed before any signed execution when absent.

Finally, and only with measured admission, run one fixed signed native entry attempt through `toy stack up`. Preserve the complete mandatory readiness denominator and `ready:false` until every required cell passes. The full assigned AT-cli-4/6/9/10 assertions, actual R0.04–05 identities, PostgreSQL, persistent stack, SIM and elapsed capacity evidence remain separate obligations.
