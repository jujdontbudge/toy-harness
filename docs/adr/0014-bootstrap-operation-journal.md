# Durable bootstrap request identities

Status: bounded implementation contract. Native execution, resource permits, persistent controllers and whole acceptance remain unavailable.

The existing Ops public `up` boundary owns the journal. Its private storage implementation hides ownership checks, SQLite transactions, request normalization and operation allocation. Deleting that implementation would move those concerns into the public adapter; it is an internal part of Ops, with no new module or public path selector.

This kitchen increment accepts only R0, the registered `r0-bootstrap` world, fake clock and fake model. After public input/environment checks, it durably records a terminal blocked operation with a stack UUID and `DEPENDENCY_UNAVAILABLE`. No helper is launched and no runtime resource permit is issued. The response uses the existing `TestStackOperationV1`, with `result:null`, a blocked canonical OperationRef and opaque operation/stack record references. It cannot claim a signed manifest, readiness, a completed native result or queued work that will continue after CLI exit. Down still refuses unattested ownership; this increment creates no resources that down could safely adopt.

The idempotency key is the normalized request UUID scoped to `stack.up`. The request digest binds release, registered world, clock and model. Missing world normalizes to `r0-bootstrap`; UUID casing normalizes to lowercase. Wait duration, invocation identity and transport timeout are read policy, not a different requested stack manifest. Separate CLI invocations with identical intent return the original operation, stack, generation and acceptance time; changed intent under the same key conflicts. A blocked operation is immutable; later implementation admission requires a new request. Each newly allocated request consumes a globally unique UInt64String generation in the same SQLite transaction. Overflow refuses allocation.

Bootstrap data is distinct from the uninstalled `_toy_ops` production store. The fixed caller-owned root is the OS account home plus `Library/Application Support/ToyBootstrap/control`. Node `os.userInfo().homedir` supplies the account database home; ambient HOME, TMPDIR, cwd and caller paths are ignored. Existing home/Library/Application Support ancestors must be owned directories without symlinks or group/world write. Newly created ToyBootstrap/control directories are owner-only. The private control root contains `owner.json`, `ops.db`, its WAL/shared-memory files and the bounded owner-derived backup intent/database/receipt namespace specified in ADR 0016. Files must be regular, singly linked, owner-only and owned by the actual unchanged real/effective UID/GID. Unknown files, unrecognized stores or an incomplete first initialization are refused without removal or adoption. No existing production file is opened or migrated.

An exclusive owner marker records a random store UUID, kernel UID/GID and control directory device/inode. It is fsynced before database creation. The database binds the same store identity. Caller-UID permissions protect against other local identities; they are not a release attestation or protection against arbitrary code already running as that same UID. Production roots and actual identities remain gated at R0.04–05. Node pathname APIs cannot eliminate an adversarial same-UID ancestor replacement; no native execution or capability is admitted on this journal alone.

The store follows canonical Ops §8: `ops_operation` and append-only `ops_event`, plus private owner/generation and stack-operation binding tables. SQLite uses WAL, FULL synchronous mode, foreign keys and a busy timeout bounded by five seconds and the invocation deadline. Node 24.21's built-in SQLite avoids another runtime dependency. Extension loading and double-quoted literals are disabled; defensive mode and bounded SQLite limits are enabled. All request, marker, generation and receipt JSON is generated and validated through Contracts before insertion and after read. Transactions allocate the request, stack identity, generation and event atomically. Database constraints enforce uniqueness and immutable request/receipt records. An incompatible schema or corrupted binding fails closed. This first schema is a fresh bootstrap store, not a production migration. Future backups must use SQLite's online backup API.

Largest-interface verification uses compiled packed `toy` subprocesses with distinct request IDs against the real local bootstrap database. Repeated requests, changed manifests, changed wait policy and concurrent identical requests must prove one durable operation without native execution. ADR 0016's backed-up V1-to-V2 transition preserves the original immutable tables/rows and adds only the migration ledger and empty owner/lease storage. Deep doctor inspects the existing store and retained online backup without initializing or migrating it. It does not test private storage functions. Future registered external OS fault cases must cover unowned/symlinked/corrupt roots and interrupted initialization/backup/migration before runtime admission. Complete AT-cli-4 and all service identity, cleanup, denial, persistent supervision and soak assertions remain pending.

Primary API evidence: [Node 24.21 OS account information](https://nodejs.org/download/release/v24.21.0/docs/api/os.html#osuserinfooptions), [exact SQLite API](https://raw.githubusercontent.com/nodejs/node/v24.21.0/doc/api/sqlite.md), and canonical planning Ops §8. Node's available-memory API is separately researched; this journal supplies no memory permit.
