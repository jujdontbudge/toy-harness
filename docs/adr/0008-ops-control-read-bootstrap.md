# Ops administrative read during bootstrap

The existing Ops module owns `OpsControlRead.status(input, context)` and `OpsControlRead.doctor(input, context)`. The CLI only normalizes registered flags, validates input/context, calls this public interface and renders its strict result. It reads no database, provider or protected service file. Context contains the selected environment, invocation UUID and bounded transport deadline; it carries no privilege/principal assertion.

The first implementation reports the compiled expected service inventory and unavailable diagnostic owners. It does not have an installed-service manifest verifier or authenticated owner transport yet. Every service/owner probe therefore explicitly reports `NOT_IMPLEMENTED` with `OWNER_TRANSPORT_NOT_IMPLEMENTED`; no PID, UID, endpoint reachability, owner result, installed release or effect is inferred. Required release defaults to R0 only because this bootstrap implementation has no installed-release discovery. Explicit release selection preserves the full inventory and selects which declared CLI capabilities are required. Capabilities reflect declaration implementation only; tested/installed/deployed remain false without digest-bound accepted records.

Status includes a null result and corresponding probe for Ops, Sources, Attention, quota/admission, cadence and publisher. Secret readiness contains each canonical registered service with state unknown. Doctor contains the same required probes and returns NOT_IMPLEMENTED/incomplete; the CLI maps that complete report to exit 5. Deep doctor additionally measures the bounded local OS resource prerequisites described in ADR 0015 and appends the registered blocked resource-admission check. This direct host observation admits no installed owner transport, service identity, lease or runtime permit. Neither path performs inference, login, sync, repair, backup, dispatch or lifecycle actions. No fixed success report or fake owner is admitted.

Canonical service IDs and CLI capabilities derive from the Contracts inventories. Additional registered owner-read checks are frozen in Contracts. They are readiness identifiers, not invented acceptance-test IDs or runnable probe registrations. Full AT-cli-3/9/10 remains pending the fixed disposable owner transports and real down/stale/denied/measured-failure matrix. Installed manifest authentication, release discovery, peer credentials, output sanitization of actual owner text, response/time bounds and test stack attestation must precede any non-null owner transport result. This bootstrap path establishes a truthful unimplemented-state read only.

Check and capability identifiers are finite generated enums derived from those inventories; an unknown identifier fails schema validation, including a claimed PASS. Doctor retains the nineteen service checks and six diagnostic-read checks. Deep doctor reuses the separately registered bootstrap.resource-admission check; the current capability registry contains the 53 declared CLI features. New owner registrations must extend the sole inventory before their response can validate. Non-null owner reads additionally require reconciliation of CLI §5.1's detailed observability with its exact §4.4 compositions; the existing canonical owner DTOs are retained unchanged rather than silently gaining keys.
